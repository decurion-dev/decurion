# How a goal flows through Decurion

Read this before any change that crosses the hub, the runner and a box.
Owner-level description: `docs/coordinator.md`. Types: `crates/decurion-proto/src/goal.rs`.

## The path of one goal

1. **Owner chat.** `goals.html` posts `POST /api/goals` (`goals::add` in `crates/decurion-hub/src/goals.rs`), which calls `Store::add_goal` in `crates/decurion-hub/src/coordinator.rs`. That queues a coordinator turn (`queue_turn`) as a row in `helper_jobs`.
2. **Coordinator.** The runner's `helper_loop` (`crates/decurion-runner/src/main.rs`) claims it with `POST /api/runner/helper/claim` (`Store::claim_helper`), and starts it in a box with `helper_run_args`: the app's code mounted read-only (`goal_copy`), no `Bash`/`Edit`/`Write`/web tools (`COORDINATOR_DISALLOWED`). It only returns text. `Store::finish_helper` reads the last JSON object (`last_json_object::<CoordinatorReply>` then `validate`); a bad shape is asked again once. The reply holds `say`, `questions`, an optional `plan`, and `remember` (notes, `save_notes`).
3. **Owner answers** with `POST /api/goals/{id}/answer` or `/say` (`goal_answer`, `goal_say`); each queues another turn.
4. **Design page.** When a reply carries a plan, the goal moves to `PlanReady` and a `design` helper job is queued. It draws the plan as an HTML page into `/out` (`read_page` in runner `lib.rs`), stored in `goal_pages` and served sandboxed by `goals::page` (`PAGE_CSP`).
5. **One approval.** `POST /api/goals/{id}/approve {plan_message_id}` (`Store::approve_plan`), or a plain yes in the goal chat sent with the plan on screen (`goal_say` with `plan_message_id`, `is_plain_yes` in `goal.rs`), refuses anything but the latest plan, then inserts one `threads` row and one `goal_pieces` row per piece, in one transaction. The goal moves to `Working`.
6. **Runner claims.** The runner polls `POST /api/runner/claim` (`Store::claim` in `store.rs`), which picks queued work for that place, sets money aside for paid accounts (moving capped work to Needs you), and returns a `Claim` (thread, app, account, budget, messages, test-key names, checkpoint).
7. **Box.** `run_in_box` (runner `main.rs`) builds the copy from the hub's base bundle (`GET /api/runner/threads/{id}/base`, `checkpoints.rs` `base_bundle`; the start commit is fixed once in `threads.base_commit`), starts the box's gate (`start_site_gate`, `gate_args`), then the agent with `run_args` (Claude) or `pi_run_args` (ChatGPT, Grok). The prompt goes in on stdin (`prompt_for`).
8. **Events.** Agent output lines become `RunEvent`s (`parse_line_hiding`, or `PiRun` for pi) and are posted to `POST /api/threads/{id}/events` (`add_event`). The hub saves each one in `events` before the board shows it. Owner messages reach a running agent through `messages.rs` and the runner's `Conversation`.
9. **Outcome.** `outcome()` in runner `main.rs` decides the state: In review only if the agent finished, left new commits (`new_commits`, fetched into the runner-owned bare repo `review_repo`), and no test key leaked (`leaked_keys`). Otherwise Failed, Queued (Max limit) or Needs you (budget). The runner moves the thread with `POST /api/threads/{id}/move`. A **research** thread (`Thread.research`, from `PlanPiece.research` at approval) needs no commits: its agent writes `/work/decurion-report.html` (`read_report`, regular files only, test keys hidden), the runner posts it to `POST /api/runner/threads/{id}/report` (`piece_reports`) before the move, the piece passes without a checker, and `github::want_send` never sends it.
10. **Review helper.** `move_thread` in `lib.rs` calls `Store::piece_thread_moved`; a piece entering In review gets a `review` job (`queue_review`). The checker runs in a throwaway copy made from the review repo (`branch_copy`), never the builder's folder. Its `ReviewVerdict` sets the piece to `passed` (and, unless a protected part holds it, accepts it for the owner under the plan's approval: Done plus `github::want_send`, then the send starts as in step 12), `fixing` (notes sent back as a follow-up message, at most `MAX_REVIEW_ROUNDS` = 2), or `needs_a_look`.
    The checker's `ReviewVerdict` may carry `evidence` (what it ran, what came of it) and `claims` (each `checked` or `guessed`), stored in `goal_pieces.review_evidence`/`review_claims`, shown on the goal page and in the pull request's "The checker" section. A later piece's claim gets `earlier_pieces_note` (finished sibling pieces' summaries) appended to its prompt in `Store::claim`, never stored. **Ask why** (`POST /api/goals/{id}/why`, `why.rs`) gathers a piece's diff and log outside any transaction into `helper_jobs.why_context` for the next coordinator turn, which keeps no notes from it.
11. **Report.** When every piece is settled, `maybe_report` queues a report turn; the goal moves to `ForReview` and the phone gets a notice.
12. **Accept sends it to GitHub; the owner merges there.** Accept (the owner's tap, a plain yes sent with `accept_on_yes`, or a goal piece passing its check, step 10) moves the thread to Done, and in the same transaction (`request_move` in `store.rs`) `github::want_send` records the send: `threads.gh_state = 'waiting'`, the branch `decurion/<app>-<n>-<title words>` (`send_branch`) and the accepted commit (the latest checkpoint's `head`). The `move_thread` handler then spawns `github::Sender::send`, one send at a time. It marks the thread `sending`, reads the work from the saved copy into the hub's bare copy of the app (`fetch_saved_code`), checks it is the accepted commit, and runs a plain `git push origin <commit>:refs/heads/<branch>` in the app's own folder, with that bare copy lent as objects (`GIT_ALTERNATE_OBJECT_DIRECTORIES`), the owner's own git sign-in and every prompt off (`push`, `push_args`). For a github.com remote it finds or opens the pull request through GitHub's API when a token is available (Settings, `Vault::get_github`, else `gh auth token`); otherwise it stores a one-tap compare link (`compare_url`). The end is recorded as `sent` or `failed`, with plain words in `gh_error` and an audit row by actor `hub`; the phone gets a notice that opens the pull request (`Pusher::notify_to`). At start, `github::resume` sends anything left `waiting` or `sending`; that is safe because a push of the same commit changes nothing and the pull request is looked for before one is opened. A failed send keeps the work Done; the owner taps Try again (`POST /api/threads/{id}/github`, `retry_send`). The by-hand route still works: the branch is in `<data>/review/<app>-<n>.git` (see `docs/help/src/review-and-merge.md`). Nothing merges.
13. **Watching the pull request.** A sent pull request (opened through the API) gets a `pr_watches` row in the send's own transaction (`pr_watch::sent`), holding its number, branch and the last commit Decurion pushed. `pr_watch::watch` (started in hub `main.rs`) looks at every open one each `POLL_SECS` with the owner's token: merged or closed ends the watch for good, and a merge tells the piece's goal (`Store::piece_merged`, which closes the goal once every piece is merged); new comments from anyone but the pull request's author go into `pr_comments` and the phone gets a notice. The app's reviewer (`apps.reviewer`) is asked for a review when the pull request is opened, and again after each fix. **Answer the comments** (`POST /api/threads/{id}/pr/fix`, `Store::start_fix`, owner-only, with a receipt) adds a thread with `fix_of` set and `base_commit` fixed to the watch's head, whose prompt carries the comments as JSON data in a marked block (`fix_prompt`). Its accept goes through step 12 to the same branch (`want_send` reads it from the watch, `check_fix_branch`), and the send refuses unless the new commit has the watch's head as an ancestor; the push itself stays plain, so git refuses a non-fast-forward too. The hub keeps that head reachable in its bare copy at `refs/decurion/pr/<thread>`, so the fix's starting bundle can be made.

## Questions inside pages

A designer or checker may ask the owner up to four questions about its page (`PageAsks` and `validate_page_questions` in `crates/decurion-proto/src/plan.rs`; the checker's go in `ReviewVerdict.questions`). `finish_helper` saves the page with its `<title>` (`pages::page_title`) and the questions in `page_questions`; questions in the wrong shape are dropped and never cost the page or the check (`ask_from_answer`, `checked_verdict` in `crates/decurion-hub/src/pages.rs`). The rule: pages still run no scripts and hold no forms, so **the hub draws the answer controls**, beside the page in its own screen. Inside the page, `goals::page` only swaps each `<div data-question="id"></div>` marker for an inert, escaped note (`pages::mark_questions`); `PAGE_CSP` keeps `sandbox` without `allow-scripts` and allows framing only by the hub itself (`frame-ancestors 'self'`). `POST /api/goals/{g}/pages/{p}/answer` (`Store::answer_page`, owner-only, with a receipt) checks the answers against the questions, records them once, and in the same transaction posts them as an owner message and queues the project lead's turn (`Store::owner_message_in`, as `goal_say` does). Tests: `crates/decurion-hub/tests/pages.rs`.

## The master plan

Each app has one ordered checklist of its goals and the to-do items found along the way (`plan_items`, `0050_master_plan.sql`; shapes in `crates/decurion-proto/src/plan.rs`; store and handlers in `crates/decurion-hub/src/plan.rs`). Every goal gets a top-level row in the transaction that starts it (`start_goal` in `coordinator.rs` calls `plan::add_goal_row`). Goal rows read their title, state and steps from the live goal each time (`Store::plan_view`, steps from the pure `goal_steps`), so they cannot fall behind. To-do rows come from the owner (`add_todo`) or the project lead's `todo` list (`plan::add_lead_todos` in `finish_helper`, talk and report turns, repeats skipped); they do nothing until the owner taps. `Store::fix_todos` starts one goal for chosen to-dos and sets their `fix_goal_id`; `close_goal` ticks them in the same transaction (`plan::tick_fixed`), stopping leaves them open. Routes are owner-only: `GET /api/apps/{id}/plan`, `POST /api/apps/{id}/plan/items`, `POST /api/plan/items/{id}`, `POST /api/plan/items/{id}/move`, `POST /api/apps/{id}/plan/fix`. Tests: `crates/decurion-hub/tests/plan.rs`.

Thread states and allowed moves: `ThreadState::can_move_to` in `crates/decurion-proto/src/lib.rs`. Review states: `ReviewState` in `goal.rs`.

## Where state lives

- Hub data folder: `DECURION_DATA`, else `%LOCALAPPDATA%\decurion` or `$HOME/decurion` (`data_dir` in hub `main.rs`). `hub.db` (SQLite), `keys.json` (owner and runner keys), `saved-work/` (bundles and checkpoints), `vault/` off Windows.
- Schema: `crates/decurion-hub/migrations/*.sql`, applied by `Store::open`. Main tables: `apps`, `threads`, `events`, `audit` (append-only), `runs` (money), `receipts`, `messages`, `goals`, `goal_messages`, `goal_pieces`, `helper_jobs`, `goal_pages`, `app_notes`, `pr_watches`, `pr_comments`, `devices`, `runners`, `checkpoints`, `test_keys`, `account_usage`, `plan_items` (the master plan), `page_questions`, `owner_keys` (last four of the owner's GitHub token), `context_files` (files the owner attached, `0047_context_files.sql`). Sending to GitHub lives in `threads.gh_*` (`0046_github.sql`).
- Attached files: `saved-work/context/app-<id>/<file id>` and `<file id>.txt` (the text the hub took out of a Word, Excel or PowerPoint file), owned by `crates/decurion-hub/src/context.rs`. Names, kinds and limits are in `crates/decurion-proto/src/context.rs`.
- Runner data folder (same rule, `data_dir` in runner `main.rs`): `workspaces/` (each thread's copy, mounted at `/work`), `review/` (runner-owned bare repos).
- Secrets: Windows Credential Manager (`decurion/claude-profile-A`, `decurion/anthropic-api`, `decurion/openai-api`, `decurion/xai-api`, `decurion/app-<id>/test-key/<NAME>`, and `decurion/github` for the owner's optional GitHub token, read only by the hub), or `DECURION_*` env vars off Windows (`Credential::env_fallback`).

## Attached files

The owner attaches files to an app (Settings) or to one goal (its Files tab), through `POST /api/apps/{id}/files` (`crates/decurion-hub/src/context.rs`). A `Claim` and a `HelperClaim` name the files the job gets (`context`: the app's own files plus its goal's). Before the agent starts, the runner fetches them as one tar (`GET /api/runner/threads/{id}/context`, or `/runner/helper/{id}/context`) and unpacks it into the job's home volume at `/home/agent/context` in a sealed throwaway box with no network (`context_import_args` in `crates/decurion-runner/src/handover.rs`), which also makes text versions of PDFs with `pdftotext`. No mount is added: the files ride in the home volume, which the box already has, and are replaced at every start. They sit outside `/work`, so they are never in a commit unless an agent copies one in. The agent learns about them from `context_prompt` (runner `lib.rs`).

## The screens

- Board `/` (`board.html`): columns by state, the composer, Settings (apps, websites, computers, accounts, test keys, phones).
- Phone inbox `/inbox` (`inbox.html`), paired by QR code (`devices.rs`), notices by Web Push (`push.rs`, `sw.js`).
- Goals `/goals` (`goals.html`). Add cloud worker `/cloud` (`cloud.html`).
- All are plain files served by `page()` in `lib.rs`; they call `/api/...` with the device cookie.

## The cloud runner

Same runner binary, run on a rented server (`docker/cloud/`, `identity.rs`). It signs up with a one-time code (`POST /runner/join`, `workers.rs`), keeps no credentials (the hub lends one per run, `POST /api/runner/threads/{id}/credential`, `secrets.rs`), and reaches only the routes in `cloud_reach`. Moving work saves a checkpoint (code bundle + session, `checkpoints.rs`, `handover.rs`) that the other computer rebuilds from. A runner with a different `RULES_VERSION` is refused and the cloud worker rebuilds itself to the hub's commit (`docker/cloud/update.sh`).
